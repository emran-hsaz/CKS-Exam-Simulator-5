Context

You must resolve issues that a CIS Benchmark tool found for the kubeadm provisioned cluster. Fix all issues via configuration and restart the affected components.

Requirements
  1. Kubelet: ensure ⎘anonymous-auth=false — FAIL
  2. Kubelet: ensure ⎘--authorization-mode is not set to AlwaysAllow — FAIL. Use Webhook authentication/authorization where possible.
  3. etcd: ensure ⎘--client-cert-auth=true — FAIL
⏱️ After restarting the kubelet the node may take up to 60 seconds to return to Ready. This node runs containerd — use crictl where the exam says docker.

1Fix the kubelet configuration
vi /var/lib/kubelet/config.yaml

Why? With anonymous auth enabled, any request to kubelet port 10250 runs as system:anonymous; combined with AlwaysAllow, an attacker can exec into any container on the node without credentials. Webhook delegates every kubelet authz decision to the API server via SubjectAccessReview.

Why? etcd stores every Secret in the cluster. Without client-cert auth, anything that can reach port 2379 can read or rewrite the whole cluster state. etcd is a static Pod — the kubelet restarts it automatically after you save; wait ~30s.

Q03Fix a Vulnerable Dockerfile and Deployment Manifest
Supply Chainsubtle-bee7 pts✓▼
Task
  1. Edit ⎘/home/candidate/subtle-bee/build/Dockerfile — fix one instruction with a prominent security issue. Do not add/remove instructions. Do not build the Dockerfile (risk of zero score).
  2. Edit ⎘/home/candidate/subtle-bee/deployment.yaml — fix one field with a prominent security issue. Do not add/remove fields.
If you need an unprivileged user, use nobody with user ID 65535.
✦ Detailed Answer & Explanation
1Dockerfile — change USER root to USER nobody
# before USER root # after USER nobody
Why? A container running as root has UID 0 in the container and (without user namespaces) UID 0 on the host if it escapes. USER nobody (65534/65535 depending on distro; the exam tells you 65535) drops privileges at the image level — the last USER instruction wins for the runtime user. It's the only instruction in the file that is inherently insecure; do not touch FROM/COPY/CMD.
2Deployment manifest — flip privileged
securityContext: privileged: false # was true — the one bad field runAsNonRoot: false # leave other fields as-is
Why? privileged: true gives the container ALL capabilities and raw device access (/dev, kernel modules) — it is effectively root on the node. It's the single most dangerous field in a Pod spec, so it's "the one field" to fix. Only modify it; adding or removing fields violates the task and loses points.
3Scoring checklist
✔Dockerfile: USER nobody (no USER root left)
✔deployment.yaml: privileged: false
✔No instructions/fields added or removed; image never built

Runtime Securityollama7 pts✓▼
Task
  1. One Pod of the application ollama is reading the sensitive file ⎘/dev/mem — identify it (Falco DaemonSet runs in ns falco, rules load from /etc/falco/rules.d/).
  2. Identify the Deployment managing that Pod and scale it to zero replicas.
⚠️ Do not modify the Deployment except scaling. Do not modify or delete any other Deployments. Only the containment is graded.
✦ Detailed Answer & Explanation
1Write a tiny Falco detection rule
cat <<'EOF' > /etc/falco/rules.d/devmem.yaml - rule: Read dev mem desc: detect any process opening /dev/mem condition: evt.type in (open, openat) and fd.name = /dev/mem output: "dev/mem opened (pod=%k8s.pod.name container=%container.name proc=%proc.name)" priority: WARNING EOF kubectl -n falco rollout restart ds falco # or: kill -HUP the falco process kubectl -n falco logs -l app.kubernetes.io/name=falco -f | grep "dev/mem"
Why Falco? Falco hooks syscalls at the kernel level, so a read of /dev/mem shows up instantly with the pod and container names via the k8s metadata enrichment — much faster than exec-ing into every pod. The %k8s.pod.name output field is what identifies the offender.

Why scale, not delete? Scaling to 0 removes the running threat while preserving the Deployment object for forensics — and the task explicitly forbids deleting or otherwise modifying Deployments.
kubectl -n ollama get deploy # offender 0/0, others untouched

Q06Implement and Extend an API Server Audit Policy
Runtime Security7 pts✓▼
Task — part 1: enable auditing
  1. Use the basic policy at ⎘/etc/kubernetes/logpolicy/audit-policy.yaml
  2. Store logs at ⎘/var/log/kubernetes/audit-logs.txt
  3. Retain a maximum of 2 logs for 10 days
Task — part 2: extend the policy to log
  1. namespaces interactions at RequestResponse level
  2. the request body of deployments interactions in namespace webapps
  3. ConfigMap and Secret interactions in all namespaces at Metadata level
  4. all other requests at Metadata level
✦ Detailed Answer & Explanation
1Add the audit flags + mounts to kube-apiserver.yaml
vi /etc/kubernetes/manifests/kube-apiserver.yaml
- --audit-policy-file=/etc/kubernetes/logpolicy/audit-policy.yaml - --audit-log-path=/var/log/kubernetes/audit-logs.txt - --audit-log-maxbackup=2 - --audit-log-maxage=10

Mount both paths into the static Pod (hostPath volumes + volumeMounts):

volumeMounts: - mountPath: /etc/kubernetes/logpolicy name: audit-policy readOnly: true - mountPath: /var/log/kubernetes name: audit-logs volumes: - hostPath: {path: /etc/kubernetes/logpolicy, type: DirectoryOrCreate} name: audit-policy - hostPath: {path: /var/log/kubernetes, type: DirectoryOrCreate} name: audit-logs
Why the mounts? The API server runs as a container — without hostPath mounts it can neither read the policy nor write the log, and it will crash-loop. maxbackup=2 = "maximum of 2 logs retained", maxage=10 = "for 10 days".
2Extend the policy (order matters — specific rules first, catch-all last)
apiVersion: audit.k8s.io/v1 kind: Policy omitStages: ["RequestReceived"] rules: # ... keep the existing "None" rules from the basic policy ... - level: RequestResponse resources: - group: "" resources: ["namespaces"] - level: Request resources: - group: "apps" resources: ["deployments"] namespaces: ["webapps"] - level: Metadata resources: - group: "" resources: ["configmaps", "secrets"] - level: Metadata # catch-all — must be LAST
Why Request for "request body"? Request logs metadata + the request body; RequestResponse also logs the response body. "Log the request body" maps exactly to level Request. Rules are evaluated top-down and the first match wins — putting the Metadata catch-all first would swallow everything.
# apply: the kubelet restarts the API server when the manifest changes; # if you only changed the policy file, force it: cd /etc/kubernetes/manifests && mv kube-apiserver.yaml .. && sleep 5 && mv ../kube-apiserver.yaml . tail /var/log/kubernetes/audit-logs.txt
3Scoring checklist
✔4 API server flags exactly as above
✔Policy: namespaces@RequestResponse, deployments(webapps)@Request, configmaps+secrets@Metadata, catch-all Metadata last
✔audit-logs.txt exists and grows
Q07NetworkPolicies for Namespace Isolation
Cluster Hardeningprod / data7 pts✓▼
Task
  1. Create NetworkPolicy ⎘deny-policy in namespace prod (labeled env: prod) to block all ingress traffic.
  2. Create NetworkPolicy ⎘allow-from-prod in namespace data (labeled env: data) to allow ingress only from Pods in the prod namespace — use the prod namespace label.
⚠️ Do not modify or delete any namespaces or Pods — only create the two NetworkPolicies.
✦ Detailed Answer & Explanation
1deny-policy — default-deny all ingress in prod
apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: deny-policy namespace: prod spec: podSelector: {} # selects ALL pods in prod policyTypes: ["Ingress"] # no ingress rules → nothing allowed
Why it works: once any NetworkPolicy selects a Pod, that Pod becomes "isolated" for the listed policyTypes; with an empty ingress list, no ingress is whitelisted, so everything is denied.
2allow-from-prod — namespace-selector allow in data
apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: allow-from-prod namespace: data spec: podSelector: {} policyTypes: ["Ingress"] ingress: - from: - namespaceSelector: matchLabels: env: prod
namespaceSelector vs podSelector: a single from entry with only a namespaceSelector allows any Pod from namespaces carrying env=prod. (Combining namespaceSelector AND podSelector in the same entry would AND them — not asked here.)
kubectl apply -f netpol.yaml kubectl -n prod get netpol; kubectl -n data get netpol

Q10Upgrade a Worker Node by One Patch Version (apt + kubeadm)
Cluster Setup6 pts✓▼
Task

The worker node runs kubelet v1.30.0 and must be upgraded to ⎘v1.30.1. SSH: ssh root@<worker-node> (password Kd7wA3fX). The v1.30 apt repo is already configured.

Steps required
  1. Identify the worker with kubectl get nodes
  2. Drain the worker node
  3. SSH in: upgrade kubeadm → kubeadm upgrade node → upgrade kubelet & kubectl → restart kubelet
  4. Uncordon the node
✦ Detailed Answer & Explanation
1Drain from the control plane
kubectl get nodes kubectl drain node01 --ignore-daemonsets --delete-emptydir-data
Why drain first? Draining cordons the node and evicts workloads gracefully so nothing is running on a kubelet that's mid-upgrade. DaemonSets can't be evicted, hence the flag.
2Upgrade on the worker (over SSH)
ssh root@node01 # password: Kd7wA3fX apt-get update apt-mark unhold kubeadm kubelet kubectl apt-get install -y kubeadm=1.30.1-1.1 kubeadm upgrade node apt-get install -y kubelet=1.30.1-1.1 kubectl=1.30.1-1.1 apt-mark hold kubeadm kubelet kubectl systemctl daemon-reload systemctl restart kubelet exit
Why kubeadm first + kubeadm upgrade node? On a worker it refreshes the local kubelet configuration from the cluster before the new kubelet starts — the documented order is always kubeadm → upgrade node → kubelet/kubectl. Exact version pinning (=1.30.1-*) is what "upgrade by one patch version" means; a plain apt-get upgrade could jump further.
3Uncordon and verify
kubectl uncordon node01 kubectl get nodes # node01 Ready, VERSION v1.30.1 (allow ~60s)
✔Worker Ready, not SchedulingDisabled, v1.30.1

Q13Harden the Docker Daemon on a Node
System Hardening7 pts✓▼
Task
  1. Remove user ⎘developer from the docker group — do not remove the user from any other group.
  2. Reconfigure and restart the Docker daemon so the Unix socket belongs to group root.
  3. Reconfigure and restart the Docker daemon so it does not listen on any TCP port.
Ensure the Kubernetes cluster is healthy afterwards.
✦ Detailed Answer & Explanation
1Remove developer from the docker group only
gpasswd -d developer docker # or: deluser developer docker groups developer # docker gone, other groups intact
Why the docker group is dangerous: membership = root-equivalent, because the member can run docker run -v /:/host --privileged and own the node. gpasswd -d removes exactly one group membership — never userdel.
2Fix the daemon configuration
vi /etc/docker/daemon.json
{ "hosts": ["unix:///var/run/docker.sock"], // removed tcp://0.0.0.0:2375 "group": "root", // socket group: was "docker" "log-driver": "json-file" }
Why? tcp://0.0.0.0:2375 is an unauthenticated, unencrypted remote root API — anyone on the network can start privileged containers. The group key sets the owner group of /var/run/docker.sock; root restricts it to root. Also check systemd drop-ins: if the unit's ExecStart contains -H tcp://… it overrides/conflicts with daemon.json — remove it there too, then:
systemctl daemon-reload systemctl restart docker ss -tlnp | grep 2375 # nothing stat -c '%U:%G' /var/run/docker.sock # root:root kubectl get nodes # cluster still healthy
Q14Configure Istio Mutual TLS (mTLS) Authentication
Cluster Hardeningapp-ns7 pts✓▼
Task
  1. PeerAuthentication named ⎘target-mtls in app-ns: STRICT mTLS for workload selector app: target-app
  2. Port-level exception: port 8080 uses PERMISSIVE mode
  3. AuthorizationPolicy named ⎘allow-client in app-ns: allow requests to target-app only from namespace client-ns
✦ Detailed Answer & Explanation
1PeerAuthentication with a port-level exception
apiVersion: security.istio.io/v1 kind: PeerAuthentication metadata: name: target-mtls namespace: app-ns spec: selector: matchLabels: app: target-app mtls: mode: STRICT portLevelMtls: 8080: mode: PERMISSIVE
STRICT vs PERMISSIVE: STRICT rejects any plaintext connection — every caller must present an Istio mTLS certificate. PERMISSIVE accepts both, which is exactly what non-mesh health/probe traffic on 8080 needs. portLevelMtls only works with a workload selector (not on mesh/namespace-wide policies).
2AuthorizationPolicy restricting the caller namespace
apiVersion: security.istio.io/v1 kind: AuthorizationPolicy metadata: name: allow-client namespace: app-ns spec: selector: matchLabels: app: target-app action: ALLOW rules: - from: - source: namespaces: ["client-ns"]
Why this locks everyone else out: once an ALLOW policy matches a workload, all requests not matched by any rule are denied by default — so listing only client-ns implicitly denies every other namespace. Source-namespace identity comes from the mTLS peer certificate, which is why STRICT mTLS and AuthorizationPolicy pair together.
kubectl -n app-ns get peerauthentication,authorizationpolicy

Q16Secure the API Server (Anonymous Auth, Node,RBAC, NodeRestriction)
Cluster Setup6 pts✓▼
Context

For testing purposes, the API server was configured to allow unauthenticated and unauthorized access.

Task
  1. Forbid anonymous authentication
  2. Use authorization mode ⎘Node,RBAC
  3. Use admission controller ⎘NodeRestriction
  4. Clean up: remove the ClusterRoleBinding ⎘system:anonymous
⚠️ kubectl currently uses anonymous access and will stop working — switch to /etc/kubernetes/admin.conf.
✦ Detailed Answer & Explanation
1Fix the API server flags
vi /etc/kubernetes/manifests/kube-apiserver.yaml
- --anonymous-auth=false # was true - --authorization-mode=Node,RBAC # was AlwaysAllow - --enable-admission-plugins=NodeRestriction
Why each flag: anonymous-auth=false rejects credential-less requests outright. Why delete the CRB? It bound cluster-admin to the system:anonymous user. Even with anonymous auth off, leaving a cluster-admin binding for an unauthenticated identity is a landmine if the flag is ever flipped back.
